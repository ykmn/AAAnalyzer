# System Audio Analyzer — план движка

## Цель

Создать Windows-приложение на .NET 8, которое без собственного драйвера и
виртуального аудиокабеля получает системный микс выбранного устройства вывода
через WASAPI loopback. Движок должен непрерывно публиковать измерения уровня и
спектра, не мешая воспроизведению звука в колонках или наушниках.

Первый результат считается готовым, когда при воспроизведении звука в браузере
или плеере движок отдаёт актуальные peak/RMS по каналам и спектр; при тишине —
корректно отображает тишину.

## Границы первой версии

Входит:

- системный микс одного устройства вывода;
- peak и RMS для каждого канала;
- спектр FFT с частотными корзинами;
- уведомления о старте, остановке, смене устройства и ошибках;
- тестируемые расчёты, отделённые от NAudio и пользовательского интерфейса.

Не входит в первую версию:

- запись WAV/MP3;
- захват звука конкретного процесса;
- LUFS, sonogram, эквалайзер и обработка аудио;
- собственный драйвер, виртуальное устройство или микрофонный захват;
- UI, настройка цветов и визуализаций.

## Техническое решение

- **Платформа:** Windows, .NET 8.
- **Захват:** NAudio `WasapiLoopbackCapture` для WASAPI loopback выбранного
  render-устройства.
- **Формат внутри движка:** нормализованные `float` samples в диапазоне
  `[-1; 1]`; исходный формат NAudio конвертируется на границе захвата.
- **Потоки:** обработчик аудиобуфера копирует данные в ограниченную очередь;
  вычисления идут в фоне. Медленный UI не должен блокировать аудиопоток.
- **Публикация:** подписчики получают неизменяемые снимки (`AnalysisFrame`),
  а не доступ к изменяемому аудиобуферу.

## Предлагаемая структура решения

```text
SystemAudioAnalyzer.sln
src/
  SystemAudioAnalyzer.Core/       # захват, преобразование и расчёты
  SystemAudioAnalyzer.App/        # UI; создаётся после готовности Core
tests/
  SystemAudioAnalyzer.Core.Tests/ # модульные тесты алгоритмов и жизненного цикла
```

Ключевые типы в `SystemAudioAnalyzer.Core`:

- `OutputDeviceInfo` — идентификатор и имя доступного устройства вывода.
- `IAudioOutputDeviceProvider` — перечисляет устройства и находит устройство
  по умолчанию.
- `SystemAudioCapture` — владеет `WasapiLoopbackCapture`, запускает и
  останавливает захват, сообщает об ошибках и передаёт PCM дальше.
- `AudioAnalyzer` — принимает нормализованные сэмплы и создаёт кадры анализа.
- `LevelMeter` — рассчитывает peak и RMS по каналам.
- `SpectrumAnalyzer` — накапливает окна, применяет окно Hann и выполняет FFT.
- `AnalysisFrame` — timestamp, частота дискретизации, уровни каналов и
  амплитуды спектральных корзин.
- `AudioAnalysisEngine` — фасад с `StartAsync`, `StopAsync`, выбором устройства
  и событием/потоком `AnalysisFrame` для UI.

Версионирование хранится в файле `VERSION.txt`: содержимое файла в виде
`VERSION`-`DATE`. Версия в формате `a.bbb`, `bbb` увеличивается при каждом
коммите, `a` — по команде разработчика. Дата текущей версии в формате
`yyyy-mm.dd`.

В папке `release\` нужен powershell-скрипт `build.ps1` для сборки/пересборки текущей версии приложения в `.exe` в папку `release\AAAnalyzer-{VERSION}`. Сборка должна быть самодостаточная: всё что требуется для запуска приложения в портативном виде должно копироваться в билд.



## Поток данных

```text
Выбранное устройство вывода
  → NAudio WasapiLoopbackCapture
  → PCM-to-float converter
  → ограниченная очередь
  → LevelMeter + SpectrumAnalyzer
  → AnalysisFrame
  → UI (следующий этап)
```

При смене системного устройства вывода UI явным образом выбирает новое
устройство, после чего движок безопасно останавливает старый захват, освобождает
ресурсы и создаёт новый. Автоматическое слежение за устройством по умолчанию
добавляется отдельной задачей после базового захвата.

## Порядок работ

Новые задания будут добавляться в файл TODO.md в виде списка с чек-боксами [ ] .

Выполненные задания отмечай [x] и переноси из TDOO.md в DONE.md. Веди файл CHANGELOG.md с кратким описанием изменений в каждой версии

### 1. Каркас и контракты

- Создать solution, библиотеку `Core` и тестовый проект на .NET 8.
- Добавить NAudio только в `Core`.
- Описать модели `OutputDeviceInfo`, `ChannelLevels`, `Spectrum`,
  `AnalysisFrame` и публичный контракт `AudioAnalysisEngine`.
- Настроить nullable reference types и предупреждения как ошибки.

Критерий: проект собирается, а тесты проверяют неизменяемость моделей и базовые
состояния движка (`Stopped`, `Starting`, `Running`, `Stopping`, `Faulted`).

### 2. Перечисление и выбор устройства

- Реализовать `IAudioOutputDeviceProvider` через NAudio/MMDeviceEnumerator.
- Возвращать только render-устройства с понятным именем и стабильным ID.
- Получать текущее устройство по умолчанию для первого запуска.
- Обработать отсутствие доступного устройства понятной ошибкой, а не
  исключением из UI.

Критерий: ручная проверка показывает колонки и наушники; unit-тесты используют
подставной provider, не зависящий от оборудования.

### 3. Захват системного микса

- Реализовать `SystemAudioCapture` вокруг `WasapiLoopbackCapture` выбранного
  устройства.
- Конвертировать входной PCM в interleaved `float` samples, сохранив частоту
  дискретизации и число каналов.
- Сделать повторные `StartAsync`/`StopAsync` безопасными и корректно освобождать
  NAudio-ресурсы при остановке и ошибке.
- Не выполнять FFT или обновление UI в обработчике `DataAvailable`.

Критерий: воспроизведение в браузере порождает непустые буферы, тишина — буферы
с нулевыми значениями; остановка не оставляет активного захвата.

### 4. Расчёт уровней

- Реализовать чистый `LevelMeter.Process(ReadOnlySpan<float>, int channels)`.
- Для каждого канала рассчитывать абсолютный peak и RMS за интервал кадра.
- Определить поведение для пустого, нулевого и неполного межканального буфера:
  пустой кадр не публикуется, неполный хвост игнорируется.
- Публиковать уровни не чаще 30 кадров/с, сохраняя последнее измерение.

Критерий: unit-тесты покрывают тишину, постоянный сигнал 0.5, отрицательный
peak, стерео с разными уровнями и неполный последний frame.

### 5. Расчёт спектра

- Начать с 4096 сэмплов на канал, окна Hann и перекрытия 75%.
- Анализировать mono-сумму каналов с нормализацией, чтобы стерео не давало
  искусственного роста уровня.
- Вынести FFT за интерфейс либо использовать маленькую изолированную
  реализацию; формат результата — линейные амплитуды с метаданными частоты и
  ширины корзины.
- Преобразование в dB и группировку полос оставить для UI-слоя/следующей задачи.

Критерий: синусоида известной частоты даёт максимум в ожидаемой корзине, тишина
не создаёт ложных пиков, а частоты за пределом Nyquist не отображаются.

### 6. Оркестрация и устойчивость

- Соединить захват, ограниченную очередь и анализатор в `AudioAnalysisEngine`.
- При переполнении очереди отбрасывать устаревший буфер и учитывать счётчик
  пропусков, а не накапливать задержку.
- Передавать ошибки захвата в `Faulted` с исходным исключением; разрешить
  последующий новый запуск.
- Добавить структурированные диагностические сообщения: устройство, формат,
  старт, стоп, пропуски и причина ошибки.

Критерий: тесты с подставным источником проверяют порядок состояний, остановку
во время обработки и восстановление после искусственной ошибки.

### 7. Проверка перед UI

- Сделать временную консольную проверку либо минимальный диагностический экран,
  который выводит device ID, формат, peak/RMS и частоту максимума спектра.
- Прогнать ручный сценарий: тишина → воспроизведение → переключение устройства
  вывода → остановка → повторный запуск.
- Зафиксировать проверенные версии Windows, устройства и известные ограничения
  (защищённый контент, приложения в exclusive mode).

Критерий: результаты анализа соответствуют воспроизводимому звуку и не требуют
виртуального аудиоустройства.

## Правила качества

- Алгоритмы уровней и FFT не зависят от NAudio и тестируются синтетическими
  сигналами.
- Все NAudio-объекты освобождаются через `Dispose` даже при частичном запуске.
- Никаких блокировок, дисковых операций или UI-вызовов в `DataAvailable`.
- Публичные значения измерений документируют единицы: peak/RMS — линейная
  амплитуда, спектр — линейная амплитуда; преобразование в dB выполняется явно.
- Изменение устройства не происходит незаметно: UI получает новое состояние и
  может показать пользователю, откуда сейчас идёт анализ.

## Критерии готовности движка

- Системный микс выбранного устройства захватывается средствами WASAPI loopback.
- При воспроизведении реально меняются peak/RMS и спектр.
- При тишине уровни и спектр стабильно близки к нулю.
- `StartAsync` / `StopAsync` можно безопасно вызывать повторно.
- Алгоритмы покрыты unit-тестами, а захват подтверждён ручной проверкой на
  целевой Windows-машине.

## Текущее состояние

Первая версия движка и диагностическая консоль готовы:

- `SystemAudioAnalyzer.Core` — WASAPI loopback через NAudio, безопасная очередь
  буферов, peak/RMS, FFT с окном Hann и асинхронный поток `AnalysisFrame`;
- `SystemAudioAnalyzer.Core.Tests` — тесты машины состояний, измерителя,
  преобразования PCM, FFT и потока данных движка;
- `SystemAudioAnalyzer.Diagnostic` — временная консоль для проверки до UI.

Движок публикует диагностические уведомления о старте, остановке, смене
устройства, отброшенных буферах и ошибках захвата. Переключение устройства
выполняется методом `SwitchDeviceAsync` без доступа к аудиобуферу из UI.

Сборка и тесты:

```powershell
dotnet test SystemAudioAnalyzer.sln
dotnet build SystemAudioAnalyzer.sln
```

Показать устройства вывода:

```powershell
dotnet run --project src/SystemAudioAnalyzer.Diagnostic -- --list
```

Запустить анализ текущего устройства по умолчанию, затем включить звук в
браузере или плеере. Консоль будет выводить peak/RMS и частоту максимума
спектра; остановка — `Ctrl+C`.

```powershell
dotnet run --project src/SystemAudioAnalyzer.Diagnostic
```

Portable-версию для Windows создаёт скрипт:

```powershell
.\release\build.ps1
```

Номер portable-папки берётся из `VERSION.txt`; готовый файл находится в
`release\AAAnalyzer-{VERSION}\AAAnalyzer.exe`.
